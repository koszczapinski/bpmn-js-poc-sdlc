# Execution plan: UI translations (EN default, PL) and English bundled diagram

Source brief: "add translations to the project; default EN, second language PL; the existing data for the chart (diagram) should be English instead of PL labels."

## Goal

The interface is available in English (default) and Polish with a switch in the header, and the bundled invoice diagram carries English labels instead of Polish ones.

## Interpretation and assumptions (recorded, not asked)

- "Data for chart" = the labels inside `src/bpmn/invoiceApproval.bpmn` (process, task, gateway, flow names). They become English.
- The diagram language does **not** follow the UI language. The modeler is the only diagram (AGENTS.md); switching language must not re-import the XML or discard edits. Names are model data.
- The selected UI language is UI state only, kept in React. It is **not persisted** (no localStorage); a reload returns to EN.
- No i18n library. The demo has a few dozen strings, so a typed dictionary plus a small `translate` function is enough (AGENTS.md: no unused dependencies).

## Scope

- Spec first: `docs/specs/invoice-approval-poc.md` (English table, AC-FLOW-1, new AC-I18N-*), traceability in `docs/ai-native-workflow.md`, README demo script, and one phrase in `AGENTS.md` (UI state may include the selected language).
- `src/i18n/`: typed EN and PL dictionaries, `translate` (interpolation, plural via `Intl.PluralRules`), `formatFinding`, provider and hook.
- `src/domain`: findings carry structured `params` next to the existing English `message`. The domain imports nothing from `src/i18n`.
- UI: all labels, status lines, panel texts, finding texts and counts, type labels. Language switch (EN | PL) in the header, `<html lang>` follows it.
- Hook messages that were English strings become message keys, so they re-render in the new language.

## Non-goals

- Translating diagram element names, bpmn-js canvas/context-pad/palette tooltips, bpmn-js import warnings, or `BpmnParseError` text (technical, shown as-is).
- Persisting the language, locale detection from the browser, more than two languages, date/number formatting.
- Any change to the validation rules or to what the modeler stores.

## Implementation Plan

Spec and tests come before code (AGENTS.md). Each phase ends with `npm run check`.

### Phase 1: Spec first

Update the spec (English diagram names, AC-FLOW-1, AC-I18N-1..5, AC-ARCH-1), AGENTS.md, the traceability table (new rows name the test files that will exist), and README.

### Phase 2: English bundled diagram

Failing assertions first (`invoiceApprovalXml.test.ts`, `App.test.tsx`), then translate the labels in the `.bpmn` file.

### Phase 3: Translation core

Failing unit tests first (dictionary parity, `translate`, `formatFinding`, domain `params`, architecture), then `src/i18n/*` and `Finding.params`.

### Phase 4: UI wiring

Failing App tests for AC-I18N-1..3 first, then provider, `UiText` messages in `useInvoiceDiagram`, components, language switch, styles.

### Phase 5: Gate

`npm run check`, `npm run build`, a manual look at the running app in both languages.

## Risks

- Placeholder drift between EN and PL (mitigated by a parity test that compares `{params}` per key).
- Polish plural forms (1 / 2-4 / 5+) handled with `Intl.PluralRules('pl')`, covered by a test.
- AGENTS.md wording change is a rule edit; flagged in the PR for the human reviewer.
